# Memory leak

Use this runbook when a process's memory usage grows steadily for hours without coming back down, or when the OOM killer terminates a process. Steady growth above 80% is a warning; above 90%, or any OOM kill of a user-facing service, is critical. Confirm the trend on the memory graph and find the process with `ps -eo pid,comm,rss --sort=-rss | head`. Check `dmesg` or `journalctl -k` for "Out of memory" lines to see what was killed. Look for a recent deploy or config change around the time growth started. As a short-term fix, propose a restart of the leaking service to free memory; restarts need human approval and only buy time. For the real fix, capture a heap dump or memory profile before restarting, roll back the deploy that introduced the leak if there is one, and open a bug for the owning team. For caches such as Redis, check that a `maxmemory` limit and eviction policy are set.
