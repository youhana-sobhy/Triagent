# Service down

Use this runbook when a service is not running, is crash looping, fails its health check, or returns HTTP 5xx or 503 errors to users. This is critical whenever users are affected, even if a health check still reports OK. Check the service state with `systemctl status <service>` or `kubectl get pods`, then read the latest logs (`journalctl -u <service> -n 200` or `kubectl logs --previous`) to find the error that made it stop. Common causes are a bad deploy, a missing config value or secret, a dependency that is down (database, cache), or the process being killed for memory. If a recent deploy caused it, roll back. If the dependency is down, follow that dependency's runbook first. If the service is simply stuck, propose a restart; restarts need human approval. After recovery, confirm the error rate is back to normal and the health check passes.
